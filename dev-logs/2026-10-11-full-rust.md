## Decision (Hafidz)

"kenapa ga full rust aja sekalian" → approved: port the Go relay core
to Rust; single binary/process. v0.7.0 (egui shell + Go sidecar)
shipped and working as the fallback; Go tree freezes as reference.

## Plan

docs/plan/FULL-RUST.md — tokio runtime on a background thread,
tokio-tungstenite both WS sides, hand-rolled CDP HTTP client, arboard

--nogui kept as the E2E surface.

## Add-on (Hafidz, same day): QR pairing

Panel shows a QR of {phone URL}/pair?c={code}; any scanner opens the
relay's landing page, which jumps to the Android app via intent://
(package com.hafidz.browserrelay, scheme browserrelay) with the
pre-paired web client as browser fallback; /app.apk serves a staged
APK from the config dir (download button only when present); the web
client auto-pairs from ?code= and scrubs the URL.

## Bugs found by the E2E (all fixed in the port, noted for parity)

1. CDP HTTP reader must honor Content-Length: Chrome's DevTools
   server keep-alives, so read-to-EOF stalls every call to timeout.
2. Frame floods can starve control messages in a shared bounded
   queue: frames now cap at 4 of 8 slots per client.
3. A phone that auths after the attach-time still went out sees
   black on static pages: hub now requests a fresh still on auth.
4. /json/close teardown is async: close-tab filters the closed id
   out of the replacement pick (Go had the same latent race).
5. chrome://omnibox-popup targets are type "page" — filtered out
   of the tab list/attach-following.
6. tray-icon pulls GTK on Linux: GUI deps are behind the default
   `gui` cargo feature, so relay-nogui builds with
   --no-default-features anywhere.

## v0.8.5 (same day, Hafidz: tray dead after panel X)

- Root cause: Windows delivers no WM_PAINT to a hidden window,
  so winit never emits RedrawRequested and egui's update()
  stops after hiding the panel. Tray events piled up in the
  channels with nobody draining them: no open, no quit.
- Fix: tray duties moved to three dedicated threads that block
  on the tray-icon channels directly (tray-click, tray-menu,
  tray-sentinel for the second-instance handoff), acting via
  the thread-safe egui::Context. Chrome mgmt calls chrome::
  fns directly. update() no longer polls the tray at all.
- E2E 23/23. relay-0.8.5.exe: 17,656,370 bytes, PE32+ GUI. Git
  tag v0.8.5.

## v0.8.6 (same day, Hafidz: panel still square — researched)

- Root cause (Microsoft Learn, "Apply rounded corners in desktop
  apps"): per-pixel alpha (transparent) windows can NEVER be
  DWM-rounded, even via the DWMWA_WINDOW_CORNER_PREFERENCE
  opt-in API. Our with_transparent(true) disqualified the
  window, so the DWM call silently did nothing (and the painted
  rounding was hidden by the opaque clear color).
- Fix: window is opaque now (the panel bg is a solid color
  anyway) — the existing DwmSetWindowAttribute(ROUNDSMALL)
  takes effect on Win11 with the native shadow. Painted 8px
  rounding stays as the Win10 fallback. Same recipe as other
  apps that hit this (transparent -> opaque + DWMWA opt-in).
- E2E 23/23. relay-0.8.6.exe: 17,656,505 bytes, PE32+ GUI. Git
  tag v0.8.6.
